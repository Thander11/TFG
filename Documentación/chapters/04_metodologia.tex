\chapter{Metodología y herramientas}
\section{Definición de la metodología aplicada}

Desde el principio se definieron cinco fases principales:

\begin{itemize}
    \item Reuniones iniciales.
    \item Búsqueda de información.
    \item Formación y entrenamiento de la nariz electrónica (e\nobreakdash-nose).
    \item Pruebas comparativas con los agentes caninos.
    \item Redacción final de la documentación.
\end{itemize}

Sin embargo, el contenido específico, la secuencia detallada y la carga de trabajo dentro de cada fase no podían fijarse de antemano, ya que dependen de la disponibilidad de recursos, de las personas implicadas y de la información que se vaya obteniendo durante el avance del proyecto. Por este motivo se adoptó un enfoque ligero, apoyado en metodologías ágiles (Scrum y Kanban), que facilita mantener un ritmo constante y una alta capacidad de adaptación ante cambios y necesidades emergentes.

Si bien se puede considerar a la Guardia Civil como el cliente final del proyecto, existen otros roles en este tipo de metodologías ágiles que también son relevantes, como el Product Owner (responsable de definir las prioridades y objetivos del proyecto), el Scrum Master (responsable de facilitar la implementación de la metodología ágil y eliminar obstáculos) y los desarrolladores. En este caso, dada la naturaleza del proyecto (un trabajo de fin de grado), el propio autor de este trabajo asume todos estos roles, gestionando tanto la planificación y ejecución del proyecto como la comunicación con los guías caninos de la Guardia Civil.

\subsubsection{Control de versiones con Git}
Para garantizar la trazabilidad y poder revertir cambios si fuera necesario, se utiliza Git como sistema de control de versiones. Esto permite mantener un historial detallado de todas las modificaciones realizadas en el código y la documentación, facilitando la gestión del proyecto.
\par

Esto se logra a traves de un repositorio privado en GitHub gestionado mediante ramas, en el que se almacena todo el código fuente, documentación, información recopilada a modo de apuntes y recursos relacionados con el proyecto.
\par

Este proceso se lleva a cabo usando GitHub Desktop, una aplicación que proporciona una interfaz gráfica para gestionar repositorios Git alojados en GitHub. Esta herramienta facilita la realización de operaciones comunes de Git, como commits, push, pull y la gestión de ramas, sin necesidad de utilizar la línea de comandos.

\subsubsection{Sprints adaptativos}
Se define como sprint a cada una de las fases anteriormente mencionadas. La duración de cada sprint se fija en funcion de una estimación del tiempo que se cree necesario para lograr los objetivos establecidos para esa fase.
\par

Antes de que inicie cada sprint (en los ultimos días del sprint anterior), se hace una organiacación aproximada de las tareas a realizar. Al comenzar el sprint, se hace una planificación más detallada de las tareas a realizar, asignando prioridades y fijando fechas de las posibles reuniones con los implicados. Durante el sprint, se revisa periódicamente el progreso y se ajustan las tareas y prioridades según sea necesario.

\subsubsection{Github Projects y Tablero Kanban}

Para la gestión de tareas, sprints y el seguimiento del progreso del proyecto, se utiliza GitHub Projects (en el repositorio anteriormente mencionado), que cuenta con un tablero Kanban integrado, como el que se muestra en la~\autoref{fig:tablero_kanban}. Este tablero permite visualizar las tareas en diferentes estados (Backlog, Ready, In progress, Done) y facilita la organización y priorización de las actividades. Cada tarea se representa como una tarjeta que puede moverse entre las columnas según su estado actual, proporcionando una visión clara del avance del proyecto.

Cada estado del tablero Kanban tiene un significado específico:
\begin{itemize}
    \item \textbf{Backlog:} Aquí se encuentran todas las tareas que se han identificado pero que aún no están listas para ser trabajadas. Estas tareas pueden ser ideas, requisitos o cualquier actividad pendiente que necesite ser planificada.
    \item \textbf{Ready:} En esta columna se colocan las tareas que están listas para ser abordadas. Esto significa que se han definido claramente, tienen los recursos necesarios y están priorizadas para su ejecución en el sprint actual.
    \item \textbf{In progress:} Esta columna contiene las tareas que están actualmente en desarrollo. Los desarrolladores trabajan activamente en estas tareas, y su progreso se monitorea para asegurar que se completen a tiempo.
    \item \textbf{Done:} Aquí se mueven las tareas que han sido completadas con éxito. Esto permite tener una visión clara de lo que se ha logrado hasta el momento y facilita la evaluación del progreso del proyecto.
\end{itemize}

\subsubsection{Sprint 1: Reuniones iniciales y elección del tema}
\textbf{Duración:} 6 de noviembre--14 de noviembre de 2025 (Completado según lo planificado).
\par

En primer lugar se llevó a cabo una reunión con los guías caninos de la Guadia Civil para discutir posibles temas para el TFG\@. Tras evaluar varias opciones, se decidió centrar el proyecto en la comparación entre una nariz electrónica y agentes caninos para la detección de hachís. Esta decisión se tomó teniendo en cuenta los recursos disponibles, la relevancia del tema y el interés personal del autor. Al principio se preguntó a Jesus Lozano Rogado (cotutor del TFG y experto en narices electrónicas) si este tema era viable y factible dentro del tiempo y recursos disponibles, a lo que respondió afirmativamente, confirmandose así el tema de este trabjo.
\par

Al comenzo de este capítulo se menciona que las fases se definieron desde el principio, lo cual no es del todo cierto. En realidad, estas fases se definieron durante este sprint, una vez que se decidió el tema del proyecto y se comprendió mejor su alcance y los recursos disponibles.
\par

\subsubsection{Sprint 2: Revisión bibliográfica y estado del arte}
\textbf{Duración:} 20 de noviembre--4 de diciembre de 2025 (Completado según lo planificado).
\par

Este sprint se dedicó a la recopilación de información relevante sobre narices electrónicas, detección canina y trabajos previos relacionados con el tema del TFG\@. Se revisaron artículos científicos (algunos de Jesus Lozano), libros y otros recursos para obtener una comprensión sólida del estado del arte en este campo. Esta información se utilizó para redactar el marco teórico del proyecto, que proporciona el contexto necesario para entender la importancia y los desafíos de la comparación entre narices electrónicas y agentes caninos en la detección de sustancias.
\par

\subsubsection{Sprint 3: Formación y entrenamiento de la nariz electrónica}
\textbf{Duración:} 5 de diciembre--25 de enero de 2026 (Retraso).

\textbf{Motivo del retraso:} Problemas de funcionamiento de la nariz electrónica para la toma de muestras y cambio de enfoque en el entrenamiento de la ANN\@.
\par

Este es el sprint más largo y complejo del proyecto, ya que implica el desarrollo del producto principal.
\par

Pese a haber recopilado información acerca de las narices electrónicas y su funciionamiento, era necesario una explicación más detallada sobre el uso. Por ello, este sprint comienza con una reunión con el Dr.\ Jesús Lozano Rogado para acordar un día en el que poder visitar el laboratorio de sensores de la Escuela de Ingenierías Industriales de Badajoz y recibir una formación práctica por parte de Cristina Brugera Salas sobre el uso de la nariz electrónica diseñada y construida por ella. Esta formación fue fundamental para entender cómo utilizar la nariz electrónica de manera efectiva y terminar de enfocar el rumbo que debía tomar el proyecto.
\par

Tras la formación se decidió que el ``entrenamiento de la nariz electrónica'' consisitiria en el entrenamiento de una red neuronal artificial (ANN) para que, a partir de los datos obtenidos por la nariz electrónica al analizar diferentes muestras, pudiera detectar la presencia de hachís. Este ``entrenamiento de la nariz electrónica'' se dividió en cinco subtareas principales:
\begin{enumerate}
    \item Toma de muestras con la nariz electrónica para crear el \textit{dataset}.
    \item Creación de un script para la limpieza y preprocesamiento de los datos obtenidos.
    \item Creación de un script para ampliar el \textit{dataset} mediante técnicas de aumento de datos.
    \item Desarrollo y entrenamiento de la ANN\@.
    \item Desarrollo de una aplicación móvil para controlar la nariz electrónica y utilizar la ANN entrenada.
\end{enumerate}

Por otra parte se vio la posivilidad de acoplar la nariz electrónica a un perro robot en caso de que sobrase tiempo (prioridad baja). Sin embargo, debido a los retrasos acumulados en este sprint, esta tarea se ha descartado para centrarse en completar las tareas principales del sprint.
\par

\subsubsection{Sprint 4: Diseño del enfoque experimental, comparación y analisis de datos}

\textbf{Motivo del retraso:} Retraso acumulado y no disponivilidad del guía hasta el 2 de febrero.

Sin embargo, debido a la agenda del guía, no fue posible realizar estas pruebas hasta el 2 de febrero de 2026. Por lo tanto, este sprint se ha dedicado principalmente a preparar el diseño experimental y analizar los datos obtenidos durante las pruebas, que se llevarán a cabo en la fecha mencionada.

\subsubsection{Limpieza y ampliación del \textit{dataset}}
Para la limpieza y preprocesamiento de los datos obtenidos durante la fase de toma de muestras, se busca crear un script que automatice este proceso y facilite la preparación del \textit{dataset} para su posterior análisis y entrenamiento de la ANN\@. Además también se buscar crear otro script para la ampliación del \textit{dataset}. Existen varias posibilidades para llevar a cabo estas tareas, entre las que se incluyen:

\begin{itemize}
    \item \textbf{Python:} Python es un lenguaje de propósito general altamente versátil que se ha convertido en el estándar de facto para la ciencia de datos y el análisis de datos. Su sintaxis legible y el abundante ecosistema de librerías especializadas (como NumPy, Pandas, Scikit-learn) lo hacen ideal para tareas de preprocesamiento. NumPy permite realizar operaciones vectorizadas eficientes sobre arrays de datos, mientras que Pandas proporciona estructuras de datos poderosas como DataFrames para manipular y transformar datos tabulares. Para el aumento de datos (data augmentation), se dispone de librerías como Imgaug o Albumentations para imágenes, y otras herramientas de sobremuestreo y suavizado para datos numéricos. La curva de aprendizaje es suave, permitiendo escribir código legible y mantenible rápidamente.
    \item \textbf{R:} R es un lenguaje estadístico especializado en análisis de datos e investigación científica. Dispone de paquetes muy maduros como dplyr (para manipulación de datos) y caret (para preprocesamiento y aumento de datos). Es particularmente potente para análisis estadísticos complejos y visualización de datos mediante ggplot2. Sin embargo, R puede resultar más lento que Python en operaciones intensivas, especialmente con grandes volúmenes de datos. Su curva de aprendizaje es más pronunciada para usuarios sin experiencia estadística, aunque es muy poderoso una vez se domina.
    \item \textbf{Bash + herramientas UNIX:} Las herramientas de línea de comandos UNIX (grep, awk, sed, cut, join) permiten realizar transformaciones de datos directamente en archivos de texto mediante tuberías (pipes). Esto es extremadamente eficiente en términos de consumo de memoria, ya que procesa el archivo línea a línea sin cargar todo en memoria. Es especialmente útil para tareas simples como filtrado, extracción de columnas y transformaciones básicas. Sin embargo, para operaciones más complejas como normalización estadística o aumento de datos basado en algoritmos sofisticados, resulta tedioso y propenso a errores. Requiere conocimiento profundo de las herramientas UNIX y puede afectar la reproducibilidad si no se documentan bien los comandos.
    \item \textbf{SQL + scripts:} Si los datos se encuentran en una base de datos relacional, SQL es una opción poderosa para filtrado, agregación y transformación de datos. Lenguajes como SQL con Python (ejecutando consultas SQL desde scripts de Python) combinan la potencia declarativa de SQL con la flexibilidad de un lenguaje de programación. Sin embargo, esto requiere que los datos estén en una base de datos, añadiendo complejidad infraestructural. Además, el aumento de datos generativo (como la síntesis de nuevas muestras) es más difícil de implementar usando solo SQL\@.
    \item \textbf{Apache Spark:} Apache Spark es un framework de procesamiento distribuido diseñado para trabajar con Big Data\@. Proporciona APIs en Python (PySpark), R (SparkR) y SQL\@. Es tremendamente escalable y puede procesar datos que no caben en una sola máquina distribuyéndolos en un cluster. Sin embargo, Spark tiene un overhead significativo de inicialización y sincronización entre nodos, lo que lo hace ineficiente para \textit{dataset}s pequeños (típicamente menor a 1 GB). Es más apropiado para pipelines de datos en producción con millones de registros distribuidos.
\end{itemize}

Sin embargo, su comunidad es más pequeña que la de Python, cuenta con menos librerías de ML maduras, y su ecosistema aún está en desarrollo.
    
    \item \textbf{Mojo:} Es un lenguaje experimental que combina la sintaxis de Python con el rendimiento de C++, estando específicamente diseñado para hardware de IA (TPUs y GPUs). A pesar de estas ventajas, es un lenguaje muy nuevo con pocos precedentes, comunidad incipiente, y librerías limitadas.

\paragraph{Frameworks}

Existen varios frameworks especializados para el desarrollo y entrenamiento de redes neuronales con características distintivas:

\begin{itemize}
    \item \textbf{PyTorch:} Es un framework basado en gráficos dinámicos que permite cambiar el modelo en pleno entrenamiento, facilitando la experimentación. Proporciona facilidad de depuración mediante herramientas estándar de Python, cuenta con un ecosistema enorme de librerías complementarias, posee una comunidad muy activa y especializada, y el autor tiene familiaridad con este framework. Sin embargo, está menos optimizado para producción comparado con TensorFlow, y presenta una curva de aprendizaje pronunciada para principiantes.
    
    \item \textbf{TensorFlow/Keras:} Está diseñado principalmente para producción y despliegue en aplicaciones reales. Ofrece una interfaz de alto nivel muy intuitiva que facilita la creación de modelos, cuenta con un ecosistema móvil robusto (TensorFlow Lite), permite crear redes complejas en pocas líneas de código, y tiene amplia documentación y tutoriales. Las desventajas incluyen que es menos flexible que PyTorch, la depuración es más complicada, y la comunidad está menos orientada hacia investigación experimental.
    
    \item \textbf{JAX:} Es un framework de bajo nivel para computación numérica con diferenciación automática, construido sobre NumPy. Proporciona flexibilidad extrema y es muy usado en investigación científica e IA\@. El enfoque funcional permite optimizaciones avanzadas y JIT compilation para mayor velocidad. Sin embargo, requiere más código para tareas simples, la comunidad es más pequeña que PyTorch/TensorFlow, y tiene menos librerías de alto nivel preimplementadas.
    
    \item \textbf{PyTorch Lightning:} Es una abstracción sobre PyTorch que simplifica el código de entrenamiento, mejorando la legibilidad y reproducibilidad. Separa la lógica del modelo de la lógica de entrenamiento, facilita el uso de GPUs/TPUs sin cambios de código, y proporciona un framework estándar para el desarrollo. Las desventajas son que añade una capa de abstracción que puede ser excesiva para prototipos rápidos, y reduce la flexibilidad en ciertos casos de uso muy específicos.
\end{itemize}

\subsubsection{Aplicación Bluetooth}

Para el desarrollo de la aplicación móvil que se comunicará con la nariz electrónica a través de Bluetooth, se han evaluado diferentes opciones de frameworks y plataformas. A continuación se presentan las herramientas consideradas:

\begin{itemize}
	\item \textbf{Flutter:} Framework multiplataforma que compila a código nativo, permitiendo crear aplicaciones para iOS y Android con una única base de código. Ofrece estabilidad en la comunicación Bluetooth mediante bibliotecas como \textit{flutter\_blue\_plus}, soporte para cargar modelos de TensorFlow Lite directamente desde assets, reactividad en la interfaz mediante Streams, y capacidad de ejecutar procesos intensivos en Isolates sin congelar la UI\@. Ideal para aplicaciones en tiempo real con restricciones de latencia.
	
	\item \textbf{React Native:} Plataforma web-first que permite código compartido entre iOS y Android. Facilita la gestión de lógica compleja mediante hooks, selector dinámico de modelos, y temporizadores. Sin embargo, la configuración de permisos iniciales (Bluetooth, storage) es tediosa y la latencia introducida por el puente JavaScript-nativo puede ser problemática para comunicaciones de tiempo real.
	
	\item \textbf{Kotlin:} Lenguaje nativo de Android que proporciona control total sobre APIs de Bluetooth (BluetoothGatt), latencia predictible, y máxima eficiencia energética mediante integración con TensorFlow Lite nativo. Requiere desarrollo separado para iOS y está limitado a ecosistema Android, aumentando complejidad de mantenimiento.
	
	\item \textbf{Capacitor:} Framework que actúa como puente entre tecnologías web (Angular, React, Vue) y APIs nativas mediante plugins. Permite ejecutar modelos con TensorFlow.js en capa web y acceder a APIs nativas de Bluetooth, pero introduce latencia adicional por su arquitectura basada en capas web, limitando viabilidad para procesamiento en tiempo real de flujos sensoriales continuos.
\end{itemize}
